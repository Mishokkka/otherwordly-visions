## 1. Итоговая оценка

Модуль уже имеет цельный рабочий замысел и заметно больше базового прототипа. Есть ApplicationV2-интерфейс, настройка Тронутых актёров, отдельные свойства потусторонних токенов, наборы изображений и звуков, автоматические таймеры, тестовые отправки, предварительная загрузка ресурсов и визуальные эффекты Canvas.

Однако версия `0.7.5` пока не готова к расширению в сторону «тяжёлого люкса». В текущей архитектуре четыре блокирующие проблемы:

1. Планировщик может создавать несколько параллельных таймеров одного набора.
2. Удалённые команды не имеют надёжной проверки полномочий отправителя.
3. Обновление видимости токенов выполняет лишние полные обходы сцены и на загрузке способно переходить в O(n²).
4. Менеджер наборов теряет несохранённые изменения при операциях с изображениями, аудио и перерисовкой интерфейса.

Сначала требуется стабилизация ядра. После неё модуль имеет хороший потенциал для превращения в полноценный режиссёр видений, а не просто генератор случайных вспышек.

## 2. Что уже сделано правильно

### 2.1. Данные разделены по назначению

Тронутость хранится на Actor, свойства потустороннего объекта на TokenDocument, наборы видений в world setting. Это разумное распределение ответственности для текущей модели данных.

### 2.2. Значения нормализуются

Код регулярно приводит числа к диапазонам, удаляет дубликаты и нормализует массивы. Это снижает вероятность повреждения данных при ручном редактировании флагов.

### 2.3. Есть явное различие между автоматической и ручной отправкой

Тестовые вспышки могут игнорировать шанс и отправляться выбранным адресатам. Это хорошая основа для будущей режиссёрской консоли.

### 2.4. Учтена предварительная загрузка медиа

Кэш изображений и аудио полезен. Проблема не в самом подходе, а в отсутствии ограничения кэша, отмены загрузки и планирования предварительной подготовки следующего события.

### 2.5. Интерфейс уже переведён на ApplicationV2

Это правильное направление для Foundry v13. Нет смысла возвращаться к ApplicationV1.

### 2.6. README честно описывает границы приватности

Модуль создаёт клиентскую иллюзию скрытия, а не защиту данных от технически подготовленного игрока. Это важное и корректное ограничение. Его следует сохранить и сделать ещё заметнее в диагностике и документации.

# 4. Блокирующие дефекты P0

## OV-001. Гонка планировщика и размножение таймеров

**Где:** `scripts/main.js:875-900`.

`syncFlashTimers()` очищает известные таймеры и создаёт новые. Callback таймера удаляет ссылку из Map, ждёт `flashVisionSet()`, затем безусловно вызывает `scheduleVisionSet(setId)`.

Проблемный сценарий:

1. Таймер срабатывает и удаляет себя из `flashTimers`.
2. Начинается `await flashVisionSet()`. Загрузка медиа может ждать до пяти секунд.
3. В этот момент другой Hook вызывает `syncFlashTimers()`.
4. Map уже не содержит старый callback, поэтому создаётся новый таймер набора.
5. Старый callback завершает `await` и создаёт ещё один таймер.
6. В Map остаётся ссылка только на последний записанный timeout. Второй продолжает работать без учёта.

Каждая последующая синхронизация в неудачный момент может увеличивать число параллельных циклов. Симптомы: слишком частые вспышки, двойное аудио, непредсказуемая нагрузка и невозможность полностью остановить автоматику.

### Исправление

Планировщик должен иметь поколение состояния и единственного владельца каждого задания.

```js
export class VisionScheduler {
  #jobs = new Map();
  #generation = 0;
  #running = false;

  reconcile(sets) {
    const generation = ++this.#generation;
    this.stopAll();
    this.#running = true;

    for (const set of sets) this.#schedule(set.id, generation);
  }

  stopAll() {
    this.#running = false;
    for (const job of this.#jobs.values()) clearTimeout(job.timer);
    this.#jobs.clear();
  }

  #schedule(setId, generation) {
    if (!this.#running || generation !== this.#generation) return;
    if (this.#jobs.has(setId)) return;

    const set = getVisionSet(setId);
    if (!isSetEligibleNow(set)) return;

    const timer = window.setTimeout(
      () => void this.#run(setId, generation),
      randomDelayMs(set)
    );

    this.#jobs.set(setId, { timer, generation });
  }

  async #run(setId, generation) {
    const job = this.#jobs.get(setId);
    if (!job || job.generation !== generation) return;
    this.#jobs.delete(setId);

    try {
      if (this.#running && generation === this.#generation) {
        const set = getVisionSet(setId);
        if (isSetEligibleNow(set)) await visionDirector.enqueueSet(set);
      }
    } finally {
      if (this.#running && generation === this.#generation) {
        this.#schedule(setId, generation);
      }
    }
  }
}
```

Обязательные свойства исправления:

- один активный timeout на один набор;
- старый callback не может воскресить отменённый цикл;
- проверка eligibility повторяется перед показом и перед повторным планированием;
- `visibilitychange`, смена сцены, владения актёром и настроек вызывают один debounced `reconcile()`;
- скрытая вкладка останавливает задания, а не только подавляет вывод.

**Приоритет:** P0, release blocker.

**Трудоёмкость:** M.

## OV-002. Удалённые команды не проверяют полномочия отправителя

**Где:** `scripts/main.js:712-756`, `1060-1077`.

Socket-команды `flashSet`, `flashImage` и `syncFlashTimers` исполняются на клиенте получателя. Проверяется только список адресатов. Происхождение сообщения не проверяется.

В fallback-ветке используется общий канал `game.socket`. Любой подключённый клиентский код может отправить пакет того же формата. В socketlib-ветке зарегистрированные remote functions также не проверяют, что инициатор является GM.

Это не даёт доступ к данным вне уже синхронизированного мира, но позволяет злоупотреблять эффектами: принудительно запускать вспышки, звук и пересинхронизацию.

### Исправление

1. Все команды должны проходить через единый command router.
2. Каждая команда получает декларацию полномочий.
3. Socketlib handler проверяет ID вызывающего пользователя.
4. Привилегированные raw-socket команды нельзя считать аутентифицированными.

```js
function requireGmUser(userId, command) {
  const user = game.users.get(userId);
  if (!user?.isGM) {
    throw new Error(`[${MODULE_ID}] Unauthorized command: ${command}`);
  }
  return user;
}

async function remoteFlashSet(setId, options = {}) {
  const callerId = resolveSocketlibCallerId(this);
  requireGmUser(callerId, "flashSet");
  return visionDirector.enqueueSetById(setId, {
    ...sanitizeRemoteOptions(options),
    source: "gm-remote"
  });
}
```

Для fallback допустимы два режима:

- рекомендуемый: socketlib становится обязательной зависимостью для удалённых GM-команд;
- совместимый: raw socket остаётся только для непривилегированных уведомлений, а ручные команды без socketlib отключаются с понятным сообщением GM.

Не следует пытаться изображать криптографическую защиту общим world-secret, который всё равно будет доставлен клиентам. Это создаст ложное чувство безопасности.

Дополнительно:

- удалённые options проходят whitelist, а не spread произвольного объекта;
- пути к медиа для `flashImage` разрешаются только из существующего набора или отдельной GM-команды;
- ограничивается частота команд на клиенте;
- в diagnostics показывается транспорт: `socketlib-secured`, `raw-unsafe`, `offline`.

**Приоритет:** P0.

**Трудоёмкость:** M.

## OV-003. Публичный API позволяет игрокам вызывать мутации и GM-интерфейс

**Где:** `scripts/main.js:278-290`, `1079-1083`, `1836-1851`.

`game.otherworldlyVisions` публикует `setTouched`, `setOtherworldly`, `flashImage`, `flashVisionSet`, `syncFlashTimers` и `openManager` для любого клиента. Внутри самих функций отсутствует единая проверка роли и прав на документ.

Foundry не позволит обычному игроку изменить чужой документ без permission, но это не заменяет контроль уровня модуля. Игрок-владелец может попытаться менять собственную Тронутость, открывать приложение, запускать локальные эффекты и вызывать внутренние операции в непредусмотренной последовательности.

### Исправление

Публичный API разделить на read-only и privileged API.

```js
const publicApi = Object.freeze({
  version: MODULE_VERSION,
  getTouched: actor => structuredClone(getTouched(actor)),
  getOtherworldly: token => structuredClone(getOtherworldly(token)),
  canCurrentUserSee: token => visibilityService.canCurrentUserSee(token),
  on: (...args) => Hooks.on(`${MODULE_ID}.${args[0]}`, args[1])
});

const gmApi = Object.freeze({
  openManager: () => requireGM() && manager.open(),
  setTouched: (actor, patch) => {
    requireGM();
    return touchedRepository.update(actor, patch);
  },
  cueSet: (setId, target) => {
    requireGM();
    return director.cueSet(setId, target);
  }
});
```

Любая mutating-функция должна самостоятельно проверять полномочия. Нельзя полагаться только на скрытую кнопку или `restricted: true` в Settings menu.

Сохранить честное ограничение: игрок с доступом к консоли и синхронизированным документам может исследовать клиентские данные. Модуль защищает игровой интерфейс, а не секреты от анализа клиента.

**Приоритет:** P0.

**Трудоёмкость:** S-M.

## OV-004. Менеджер теряет несохранённые данные при перерисовке

**Где:** `templates/manager.hbs`, обработчики `scripts/main.js:1429-1700`.

Редактирование набора происходит непосредственно в DOM. Большинство действий после добавления, удаления, импорта или теста вызывают `this.render()`. Значения полей, которые пользователь изменил, но не сохранил кнопкой набора, исчезают.

Особенно опасный сценарий:

1. GM меняет задержку, вероятность, длительность и визуальные параметры.
2. Нажимает «добавить изображение» или удаляет существующее.
3. Обработчик сохраняет только медиа-операцию.
4. Приложение перерисовывается.
5. Остальные изменения возвращаются к предыдущим сохранённым значениям без предупреждения.

Это прямой риск потери работы.

### Исправление

Нужен draft model, независимый от DOM.

- При открытии редактора создаётся `VisionSetDraft`.
- `input` и `change` обновляют draft с debounce.
- Медиа-операции работают с draft, а не напрямую с setting.
- Сохранение валидирует и коммитит весь draft.
- Dirty state показывается в заголовке набора.
- Закрытие окна, смена набора и удаление требуют решения: сохранить, отбросить, отменить.
- Тест по умолчанию использует draft, чтобы GM слышал и видел именно текущие параметры.

Минимальный временный патч до полноценного draft:

```js
static async addImage(event, target) {
  const panel = target.closest("[data-set-id]");
  await this.#commitPanel(panel, { silent: true });
  const picked = await pickImage();
  if (!picked) return;
  await visionSetRepository.appendImage(panel.dataset.setId, picked);
  await this.render({ force: true });
}
```

Но целевой вариант должен уйти от «DOM как хранилище состояния».

**Приоритет:** P0.

**Трудоёмкость:** M-L.

# 5. Высокий приоритет P1

## OV-005. Полный обход токенов вызывается для каждого `drawToken`

**Где:** `scripts/main.js:696-710`, `1884-1887`.

`drawToken` для одного токена вызывает `refreshTokenVisibility()`, который проходит по всем токенам сцены. При начальном рисовании N токенов это даёт приблизительно N полных обходов по N токенам.

Внутри каждой проверки видимости дополнительно собирается список всех актёров, принадлежащих текущему пользователю (`scripts/main.js:407-415`). Итоговая стоимость растёт быстрее, чем необходимо.

### Исправление

- `drawToken(token)` обновляет только этот token.
- Полный refresh выполняется только при изменении профиля зрителя или глобальных правил.
- Полный refresh проходит через debounce на один animation frame.
- Профиль зрителя кэшируется.
- Кэш инвалидируется при `updateActor`, `updateUser`, смене character, ownership и соответствующих flags.

```js
function refreshOneToken(token) {
  token.renderFlags?.set({ refreshVisibility: true });
  tokenEffects.reconcile(token);
}

const refreshAllTokens = foundry.utils.debounce(() => {
  for (const token of canvas.tokens?.placeables ?? []) refreshOneToken(token);
}, 25);

Hooks.on("drawToken", refreshOneToken);
Hooks.on("updateToken", (doc, changes) => {
  const token = doc.object;
  if (token && affectsOtherworldlyState(changes)) refreshOneToken(token);
});
```

Нужно использовать штатный механизм render flags Foundry вместо прямого назначения `token.visible`.

**Приоритет:** P1.

**Трудоёмкость:** M.

## OV-006. Прямое `token.visible = token.isVisible` обходит жизненный цикл Canvas

**Где:** `scripts/main.js:704`.

`visible` является свойством PIXI DisplayObject. Прямое присваивание меняет отображение контейнера, но не сообщает другим подсистемам Foundry, что видимость должна быть пересчитана. Это может расходиться с targeting, controls, vision/light sources и render flags.

### Исправление

Использовать стандартный путь обновления:

```js
token.renderFlags.set({ refreshVisibility: true });
```

Точный набор флагов проверить на v13.351 в runtime. При необходимости вызывать публичный refresh механизма Canvas, но не приватный метод без адаптера версии.

Прямой `Token#isVisible` wrapper допустим только как точка вычисления итоговой визуальной доступности. Он не должен сопровождаться ручным управлением PIXI visibility в обход Canvas.

**Приоритет:** P1.

**Трудоёмкость:** S-M.

## OV-007. Прямой monkey patch getter конфликтует с другими модулями и не имеет реального fallback

**Где:** `scripts/main.js:475-535`.

При отсутствии libWrapper код переопределяет descriptor `Token.prototype.isVisible`. Это может:

- перезаписать патч другого модуля;
- быть перезаписано модулем, загрузившимся позже;
- сломаться при изменении descriptor;
- затруднить корректное снятие патча;
- вести себя по-разному при v13/v14.

Сообщение о «visual fallback» вводит в заблуждение. Если getter не найден, фактического механизма скрытия не создаётся.

### Исправление

Рекомендуемая модель:

1. `lib-wrapper` добавить как recommended dependency.
2. В diagnostics явно показывать состояние патча.
3. При провале wrapper не заявлять, что скрытие работает.
4. Для доверенной персональной установки можно оставить direct fallback под отдельной настройкой «режим совместимости», выключенной по умолчанию.
5. Добавить health check после canvasReady: взять тестовый потусторонний token и проверить соответствие ожидаемого `isVisible`.

Не следует скрывать token только CSS/alpha как основной fallback. Прозрачный token может сохранять интерактивность и связанные источники.

**Приоритет:** P1.

**Трудоёмкость:** M.

## OV-008. Требуется аудит утечек через свет, зрение, бой и интерактивность

**Статус:** риск, требующий runtime-проверки.

Патч `isVisible` скрывает представление token, но потусторонний TokenDocument может влиять на игру другими путями:

- источник света;
- источник зрения;
- combat tracker;
- targeting и hover;
- nameplate, bars и effects;
- collision и wall interaction;
- активные ауры сторонних модулей;
- звуки, привязанные к токену;
- отображение в списках и HUD.

### Исправление

Создать явный режим «Полностью призрачный»:

- принудительно выключает light и vision source для невидимого зрителя;
- запрещает targeting и hover interaction;
- не показывает nameplate, bars, effects и status icons;
- имеет отдельную опцию участия в collision;
- имеет отдельную опцию видимости в combat tracker;
- не меняет сам TokenDocument для всех клиентов, если это можно решить client-side adapter.

Все пункты должны быть протестированы с обычным токеном, hidden token, GM vision и несколькими игроками.

**Приоритет:** P1 до 1.0.

**Трудоёмкость:** M-L.

## OV-009. Визуальные эффекты изменяют корневой `token.alpha`

**Где:** `scripts/main.js:674-693`.

Модуль восстанавливает alpha из `token.document.alpha` и затем задаёт viewer opacity. Это может конфликтовать с временным alpha Foundry, hover, hidden-state, анимациями и другими модулями.

### Исправление

- не менять root `token.alpha`;
- применять прозрачность к mesh/sprite или отдельному effect container;
- хранить исходное transient-состояние только на время собственного эффекта;
- не «восстанавливать» значение, которое модуль не владеет;
- контейнер эффекта вставлять в предсказуемый слой, а не последним child поверх bars/nameplate.

Нужен небольшой Canvas adapter, который знает структуру Token v13 и отдельно v14.

**Приоритет:** P1.

**Трудоёмкость:** M.

## OV-010. ApplicationV2 редакторы имеют одинаковые ID и не очищают реестры

**Где:** `scripts/main.js:1145-1260`.

Каждый actor editor получает ID `otherworldly-visions-actor-editor`, каждый token editor получает одинаковый token ID. При этом приложения хранятся в Map по документам и допускают одновременное открытие нескольких экземпляров. Это создаёт коллизии DOM/Application ID.

Maps не очищаются при закрытии. Классы редакторов создаются заново при каждом первом открытии документа.

### Исправление

- определить классы один раз в `init`;
- формировать unique ID из UUID документа;
- очищать Map в `_onClose`;
- перед каждым действием проверять, что документ не удалён;
- использовать scene UUID для token, чтобы одинаковые token IDs на разных сценах не сталкивались.

```js
constructor(actor, options = {}) {
  super({
    ...options,
    id: `${MODULE_ID}-actor-${slugify(actor.uuid)}`
  });
  this.actor = actor;
}

async _onClose(options) {
  actorEditors.delete(this.actor.uuid);
  return super._onClose(options);
}
```

**Приоритет:** P1.

**Трудоёмкость:** S.

## OV-011. `_onRender` не соблюдает async-контракт ApplicationV2

**Где:** `scripts/main.js:1417-1427`.

Метод вызывает `super._onRender` без `await`. В ApplicationV2 жизненный цикл асинхронный. Это может давать гонки при расширении приложения или работе mixin.

### Исправление

```js
async _onRender(context, options) {
  await super._onRender(context, options);
  this.#bindAutosizeTextareas();
}
```

Следует также избегать повторного навешивания anonymous listeners на каждый render. Использовать AbortController на цикл render или event delegation.

**Приоритет:** P1.

**Трудоёмкость:** S.

## OV-012. Переименование и удаление наборов оставляет несогласованные ссылки

**Где:** `scripts/main.js:1532-1555`.

При переименовании сначала сохраняется новый объект sets, затем последовательно обновляются Actor flags. Ошибка посередине оставит часть ссылок старой, часть новой. При удалении наборов ссылки намеренно остаются на актёрах.

Параллельное редактирование двумя GM дополнительно создаёт lost update, потому что каждый сохраняет весь объект world setting.

### Исправление

1. Ввести постоянный UUID набора, который не меняется при редактировании пользовательского slug/name.
2. Actor должен ссылаться на UUID, а не изменяемый ID.
3. Удаление предлагает: удалить ссылки, заменить другим набором, оставить orphan.
4. Миграция создаёт backup и отчёт.
5. Добавить Repair tool для orphan references и duplicate IDs.
6. Для нескольких GM использовать revision field и optimistic concurrency check.

```js
{
  schemaVersion: 2,
  revision: 17,
  sets: {
    "0f2...uuid": {
      uuid: "0f2...uuid",
      slug: "yellow-void",
      name: "Жёлтая пустота"
    }
  }
}
```

**Приоритет:** P1.

**Трудоёмкость:** L.

## OV-013. Параллельные вспышки не имеют очереди и политики приоритетов

**Где:** `scripts/main.js:995-1043`.

`flashImage()` возвращается после одного animation frame, а не после окончания эффекта. Следующая вспышка заменяет содержимое layer через `replaceChildren()`. Звуки могут продолжить проигрываться независимо.

В результате:

- автоматическая вспышка может перебить ручную;
- две ручные команды могут взаимно уничтожить изображение;
- старый звук остаётся после замены картинки;
- таймер считает событие завершённым почти сразу.

### Исправление

Ввести `VisionDirector` и очередь:

- приоритеты: emergency stop > manual GM cue > scripted trigger > random;
- режимы конфликта: queue, replace, drop, merge;
- не более одного основного визуального cue одновременно;
- отдельный аудиоканал с fade/stop;
- Promise завершается после полного жизненного цикла;
- ручной cue по умолчанию прерывает random cue;
- кнопка «остановить всё».

```js
await director.enqueue({
  type: "vision",
  priority: PRIORITY.MANUAL,
  conflict: "replace-lower",
  payload
});
```

**Приоритет:** P1.

**Трудоёмкость:** M-L.

## OV-014. Таймеры продолжают жить в скрытой вкладке

**Где:** `scripts/main.js:1010-1016`.

**Где:** `scripts/main.js:80-85`.

`Promise.race` оставляет timeout жить после успешной загрузки. Это небольшой дефект, но он легко исправляется через explicit timer cleanup или AbortSignal.

## OV-018. Загрузка в момент события создаёт задержку до пяти секунд

Сюрприз может появиться заметно позже срабатывания таймера. Для хоррор-сцены это ломает ритм.

Исправление: scheduler заранее выбирает несколько кандидатов без фиксации окончательного результата и подогревает assets. Окончательный выбор делается перед cue с учётом no-repeat history.

## OV-019. Все наборы открыты и все thumbnails загружаются сразу

**Где:** `templates/manager.hbs:73`, изображения без lazy attributes.

При десятках наборов и сотнях assets менеджер создаёт большой DOM, загружает изображения и становится тяжёлым.

Исправление:

- открывать только активный набор;
- сохранять active set и scroll state;
- `loading="lazy" decoding="async"`;
- виртуализация или пагинация asset grid;
- поиск и фильтр;
- отдельная панель редактора вместо полного editor внутри каждого `<details>`.

## OV-020. Вкладка всегда сбрасывается на «Наборы»

**Где:** `templates/manager.hbs:47-50`.

Radio `checked` зашит в шаблоне. Любой render сбрасывает вкладку. Это особенно раздражает при работе с актёрами и токенами.

Исправление: использовать ApplicationV2 tabs либо хранить `activeTab` в состоянии приложения. Сохранять также активный набор, scroll и focus.

## OV-021. Скрытые radio-tabs недоступны клавиатуре

CSS скрывает radio через `display: none`, а labels используются как навигация. Такая схема ухудшает keyboard navigation и semantics.

Исправление: настоящий tablist с `role="tab"`, `aria-selected`, arrow navigation, Home/End и фокусом. Предпочтительно штатный tab controller ApplicationV2.

## OV-022. Иконки и HUD-кнопка не имеют полного accessibility-контракта

Token HUD создаёт clickable `<div>`. Иконки в нескольких кнопках не имеют понятного `aria-label`/tooltip.

Исправление:

- использовать `<button type="button">`;
- `aria-label` и локализованный tooltip;
- Enter/Space;
- visible focus ring;
- не передавать смысл только цветом.

## OV-023. CSS нарушает owner-file принципы

CSS содержит 1424 строки и поздний блок `0.7.5: hard dark theme pass` (`styles/otherworldly-visions.css:1166-1424`), который повторно переопределяет ранние правила через `!important`.

Проблемы:

- многие `.ov-*` правила не ограничены корнем приложения;
- широкие селекторы `.window-content:has(...)` могут влиять на чужие окна;
- одна тема фактически определена дважды;
- повторяются группы selector/property;
- specificity регулируется поздним hard override, а не архитектурой;
- Canvas overlay, manager и editors смешаны в одном файле.

### Целевая CSS-модель

```css
@layer otherworldly-visions.tokens,
       otherworldly-visions.apps,
       otherworldly-visions.overlay,
       otherworldly-visions.accessibility;

@layer otherworldly-visions.apps {
  .application.otherworldly-visions {
    --ov-surface-0: #080b10;
    --ov-surface-1: #111821;
    --ov-text: #eef3fb;
  }

  .application.otherworldly-visions .ov-set-card {
    background: var(--ov-surface-1);
  }
}
```

Правила:

- каждый UI-селектор начинается с owner root;
- глобальными остаются только уникальные overlay/root IDs и Canvas-owned контейнеры;
- запрет на `:has()` для захвата `.window-content`;
- `!important` допустим только для доказанного конфликта Foundry, с комментарием;
- общие design tokens определяются один раз;
- manager/editor/token/overlay разделяются по файлам.

## OV-024. Размер менеджера жёсткий и плохо адаптируется

Менеджер ориентирован примерно на `1180x860`, а responsive-правила зависят от viewport. На небольшом экране или при узком окне содержимое может быть неудобным.

# 7. UI/UX: целевая модель

## 7.1. Менеджер должен стать рабочей станцией, а не длинной формой

Предлагаемая компоновка:

```text
┌────────────────────────────────────────────────────────────────────┐
│ Otherworldly Visions  [transport] [scheduler] [stop all] [help]   │
├───────────────┬───────────────────────────────────┬────────────────┤
│ Sets          │ Set editor                        │ Live inspector │
│ Search        │ General / Schedule / Visual       │ Recipients     │
│ + New         │ Audio / Assets / Triggers         │ Next event     │
│               │                                   │ Asset health   │
│ • Yellow Void │                                   │ Recent cues    │
│ • Faces       │                                   │                │
│ • Blood       │                                   │                │
├───────────────┴───────────────────────────────────┴────────────────┤
│ Unsaved changes                         [Revert] [Save] [Test]     │
└────────────────────────────────────────────────────────────────────┘
```

Основные принципы:

- слева компактный список наборов;
- в центре редактируется один выбранный набор;
- справа всегда видны адресаты, статус assets и ближайший автоматический запуск;
- footer показывает dirty state и действия;
- вкладки верхнего уровня: Director, Sets, Touched, Tokens, Diagnostics;
- настройки не перерисовывают весь manager без необходимости.

## 7.2. Работа с вероятностью

Поле `0..1` технически корректно, но для GM неудобно. Показывать процент `0..100%`, хранить нормализованное значение внутри.

Дополнительно показывать понятную модель:

- интервал проверки;
- вероятность после проверки;
- приблизительный средний интервал появления;
- cooldown после успешного показа.

Пример: «Проверка каждые 4-8 минут, шанс 35%, ожидаемо примерно раз в 17 минут». Это статистическая оценка, а не обещание.

## 7.3. Выбор адресатов

Нужен live preview:

| Пользователь | Персонаж | Тронут | Набор назначен | Получит cue | Причина |
|---|---|---:|---:|---:|---|
| Player 1 | Мартен | Да | Да | Да | rank 3, tags совпали |
| Player 2 | Ивона | Да | Нет | Нет | набор не назначен |
| Player 3 | Нет character | Нет | Нет | Нет | нет доступного actor |

Для токена аналогичная матрица: кто видит и почему. Это снимет большую часть вопросов «почему игрок не видит».

## 7.4. Настройки игрока

Игрок должен контролировать только локальную безопасность и интенсивность, не игровые права:

- общий volume cap;
- opacity cap;
- reduced motion;
- photosensitivity safe mode;
- отключение blur/rotation/flicker;
- запрет воспроизведения в скрытой вкладке;
- минимальный интервал между cues;
- тест экрана и звука;
- emergency mute на сессию.

GM должен видеть, что player включил safety mode, но не должен иметь возможность удалённо его отключить.

## 7.5. Подтверждение опасных действий

Подтверждение требуется для:

- теста «всем игрокам»;
- удаления набора;
- массовой очистки ссылок;
- замены набора у многих актёров;
- отмены всех текущих cues;
- запуска потенциально яркого/громкого пресета без safety metadata.

Подтверждение не требуется для обычного локального preview GM.

# 8. «Тяжёлый люкс»: функции, которые действительно усилят модуль

## 8.1. Vision Director

Центральная режиссёрская консоль:

- cue stack;
- ручной запуск набора, отдельного asset или последовательности;
- адресаты: пользователь, actor, группа, все Тронутые, выбранные tokens;
- countdown 3/2/1 для синхронного запуска;
- queue/replace/drop policy;
- live status клиентов;
- cancel current и stop all;
- история последних событий;
- повтор последнего cue;
- preview только GM.

Это самая ценная функция после стабилизации.

## 8.2. Weighted shuffle без повторов

Простой `random()` часто повторяет один и тот же asset. Нужны:

- weight на asset;
- shuffle bag;
- no-repeat window;
- cooldown на конкретный asset;
- глобальный cooldown набора;
- максимальное число показов за сессию;
- reset history вручную или при начале сессии.

## 8.3. Связанные медиа-сцены

Не только общий пул изображений и общий пул звуков, а cue entries:

```json
{
  "image": "visions/face-01.webp",
  "audio": "visions/whisper-01.ogg",
  "weight": 2,
  "duration": 620,
  "caption": "Не оборачивайся",
  "tags": ["face", "close", "whisper"],
  "safety": ["flicker", "loud"]
}
```

Общий sound pool можно сохранить как fallback.

## 8.4. Последовательности и beats

Набор может содержать timeline:

```text
0 ms      тихий звук
120 ms    первая картинка
500 ms    затемнение
720 ms    вторая картинка
1100 ms   whisper/caption
1600 ms   окончание
```

Редактор timeline не нужен в первой версии. Достаточно списка шагов с delay, duration и transition.

## 8.5. Система триггеров

Триггеры должны быть адаптерами, а не hardcoded Hooks внутри набора.

Базовые:

- manual;
- random schedule;
- начало/конец боя;
- начало хода;
- token входит в Region;
- token приближается к потустороннему объекту;
- смена Scene;
- изменение darkness;
- Actor получает damage/condition;
- ChatMessage или roll outcome;
- macro/API hook.

Forbidden Lands adapter после отдельной проверки API системы:

- push броска;
- провал или большое число banes;
- spell casting и mishap;
- critical injury;
- состояние персонажа;
- трата/изменение подходящего системного ресурса;
- особые предметы, таланты и эффекты.

Системные поля и hooks нельзя зашивать без проверки текущей версии Forbidden Lands. Adapter должен отключаться чисто, не ломая core.

## 8.6. Прогрессивное раскрытие потусторонних объектов

Вместо бинарного «видит/не видит»:

1. Ничего.
2. Нечёткий силуэт.
3. Искажение пространства.
4. Краткие проявления.
5. Полное видение.
6. Узнанный объект, сохраняющийся в памяти персонажа.

Состояние можно хранить на User или Actor в зависимости от правил мира. Это позволит делать расследования и персональную мистику.

## 8.7. Условия видимости токена

Дополнить rank/tags:

- дистанция;
- line of sight;
- elevation;
- Scene/Region;
- darkness range;
- время с момента входа на сцену;
- шанс краткого проявления;
- раскрытие после конкретного cue;
- состояние Actor;
- индивидуальные исключения пользователей.

Нужен визуальный rule builder, но внутренне правила должны храниться как нормализованный AST, а не произвольный JavaScript.

## 8.8. Scene Otherworld Layer

GM-режим для работы с потусторонним слоем:

- подсветить все потусторонние tokens;
- массово назначать properties;
- временно показать глазами выбранного игрока;
- легенда состояний и причин видимости;
- paint/bulk edit выбранных tokens;
- режим «manifest for 2 seconds»;
- scene presets.

## 8.9. Asset Library

- папки и drag-and-drop;
- поиск по имени и tags;
- thumbnails;
- waveform/audio preview;
- массовый import;
- deduplication;
- metadata editor;
- конвертация путей при переносе папки;
- выявление missing assets;
- экспорт/импорт наборов JSON;
- duplicate set;
- reusable presets.

Сам модуль не должен перекодировать медиа. Он может давать рекомендации по WebP/AVIF/OGG и размеры файлов.

## 8.10. Диагностика

Отдельная вкладка должна показывать:

- версия Foundry, системы и модуля;
- libWrapper/socketlib status;
- состояние visibility patch;
- число видимых/скрытых tokens;
- профиль текущего зрителя;
- активные scheduler jobs;
- время следующего события;
- очередь Director;
- кэш медиа;
- missing assets;
- orphan references;
- последние socket-команды и ошибки;
- кнопка копирования anonymized diagnostic report.

## 8.11. Session Journal

Локальный или world log:

- время cue;
- источник trigger;
- набор и asset;
- адресаты;
- показан/подавлен/ошибка;
- safety suppression;
- длительность;
- инициатор GM.

По умолчанию не записывать полные локальные пути в export, если журнал предназначен для отправки разработчику.

## 8.12. Public Hooks API

Вместо публикации внутренних функций:

```js
Hooks.callAll("otherworldly-visions.beforeCue", cue);
Hooks.callAll("otherworldly-visions.afterCue", result);
Hooks.callAll("otherworldly-visions.visibilityChanged", token, state);
Hooks.callAll("otherworldly-visions.schedulerChanged", snapshot);
```

Публичный API должен быть versioned и документирован. Внутренние репозитории и scheduler наружу не выдаются.

# 15. Финальный вывод

Модуль не требует переписывания с нуля. Его основная модель пригодна, а существующий функционал можно сохранить. Требуется контролируемое разделение монолита на сервисы и исправление четырёх базовых контуров: scheduler, socket authorization, Canvas visibility и UI state.

«Тяжёлый люкс» здесь должен означать не количество случайных эффектов, а режиссёрскую управляемость:

- GM точно понимает, кто что увидит и почему;
- ручные и автоматические события не конфликтуют;
- игрок имеет локальные safety controls;
- наборы не повторяются бессмысленно;
- потусторонние объекты раскрываются постепенно;
- module health виден без консоли;
- изменения данных мигрируют и восстанавливаются;
- интерфейс сохраняет состояние и не теряет правки.

После выполнения этапов `0.8.0-0.10.0` модуль будет иметь достаточно устойчивое основание для Director, triggers, progressive reveal и глубокой интеграции с Forbidden Lands.
